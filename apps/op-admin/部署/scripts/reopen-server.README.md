# 重开后台数据库

适用当前 `common(wao)` 分支。脚本不自动连接历史对话中的 main 服务器，不操作游戏服。
脚本：`reopen-server.js`，沿用同目录 `config.js` 和 mysql2；默认模式仅预览。

## 已确定的处理规则

1. 执行前完整备份目标数据库（表、数据、触发器、存储过程、事件），生成 SHA-256 校验清单。
2. 保留当前玩家平台币余额，加回 `paymentrecords` 中平台币方式、状态 3/4、`ptb_change < 0` 的实际扣款，按 `-ptb_change` 汇总，不按商品金额猜测。
3. 每个获返还用户写一条 `paymentrecords` “重开平台币返还”正向流水：用户ID、批次号、前余额、返还额、后余额。额外写入 `server_reopen_refunds`，便于核对；批次记录在 `server_reopen_runs`。这些记录不会被本脚本清除，也不算现金充值。
4. 删除已返还的原消费记录，以及状态0/1/2且 ptb_change 为0或空的未支付/处理中/失败订单。保留成功现金订单（包括 Steam）、平台币充值/赠送正向流水、管理员余额、转账流水、结算、CDK 使用状态及兑换记录。不会照抄 `clean_server.sql` 清零余额或重新开放已用 CDK。
5. 清空存在的角色、礼包购买记录、业务日志、用户登录日志、GM日志、日报、LTV。具体表名在脚本 CLEAN 列表中，预览展示笔数。不存在的可选表会跳过。
6. 每个主账号保留最小 ID 的小号（按自增ID视为最早），保留名称，清空 wuid；删除其余小号。没有小号的账号新建一个。**不会重置自增序号，也不会永久把创建上限改成1。**

7. 第五步服务器表按主键 `id ASC` 只保留第一条，配置字段原样保留，不重编号、不清游戏服真实数据库。现金成功订单的历史区服ID原样保留。

**每一步由你手动运行，不自动串联。每一步各自使用一个事务**，本步失败回滚本步，前面已经完成的步骤保持提交状态。
阶段依次为 `backed_up → refunded → cleaned → subusers_reset → servers_reset`；脚本检查顺序，拒绝跳步和重复退款，有未完成批次时禁止另起批次。
步骤间持续保持停服。余额、小号、消费来源、清理表数量等检查点发生变化会阻止下一步，避免拿旧备份继续清理。

## 预览

和同目录其他脚本一样，直接使用 `config.js` 导出的 `DB_CONFIG`。已有配置可用时，无需额外设置环境变量：

```sh
node reopen-server.js preview --report-dir=/data/reopen-preview
```

如需切换数据库，可按其他脚本的方式用 `DB_HOST`、`DB_PORT`、`DB_USER`、`DB_PASSWORD`、`DB_NAME` 覆盖。连接成功会显示地址、端口和数据库名，不打印密码。正式执行的 `--confirm-db` 必须与当前实际连接的库名一致。

预览只 SELECT，不改数据库。显示预计返还人数/总额、清理笔数、小号调整数量和阻断项；JSON 明细含每个用户前后余额、小号映射。文件可能含玩家信息，权限为 600。

## 正式执行

先停服维护：停止注册、登录、角色上报、商城、支付发起及回调处理、所有写库服务和 cron、异步发货/补单/自动发奖任务；不只是停止游戏服。确认不存在还会继续扣款/补发的外部任务。库内未支付且无平台币资金变动的订单，由第三步自动删除，不阻止备份或退款。脚本的命名锁只防止本脚本并发，无法替代停服。

以下每条命令都要你单独执行，确认输出后再运行下一条。数据库名换成 `config.js` 实际连接的库名，所有步骤使用同一个批次号。

**第一步：完整备份（不退款、不清理）。**

```sh
node reopen-server.js backup --run-id=wao-reopen-20261010 --confirm-db=quantum_db --backup-dir=/data/reopen-backups --maintenance-confirmed
```

**第二步：退款并保存逐用户流水（不清理原消费或角色）。**

```sh
node reopen-server.js refund --run-id=wao-reopen-20261010 --confirm-db=quantum_db --maintenance-confirmed
```

**第三步：清理已返还消费、角色、礼包记录及指定日志/统计表（不改小号）。**

```sh
node reopen-server.js clean --run-id=wao-reopen-20261010 --confirm-db=quantum_db --maintenance-confirmed
```

**第四步：每账号保留最早一个小号，清空其角色关联，无小号则创建。**

```sh
node reopen-server.js reset-subusers --run-id=wao-reopen-20261010 --confirm-db=quantum_db --maintenance-confirmed
```

**第五步：服务器配置只保留 ID 最小的一条。**

```sh
node reopen-server.js reset-servers --run-id=wao-reopen-20261010 --confirm-db=quantum_db --maintenance-confirmed
```

已用旧版完成四步、状态为 `complete` 的批次，也可以直接执行第五步，无需重新备份或退款。第五步只检查批次顺序、原备份/计划文件及服务器表自身的锁、外键和触发器，不要求旧余额/订单/日志检查点保持不变，也不修改这些数据。此步还会生成 `servers-before-reset-*.json` 快照（含服务器连接配置，权限600）。如保留的第一条是测试服/停用服，请先确认是否确实要保留它；脚本按ID取第一条，不擅自选其他服务器。服务器缓存和客户端静态区服列表需在恢复服务前同步更新，脚本不清共享 Redis。

随时查看批次进度（只读）：

```sh
node reopen-server.js status --run-id=wao-reopen-20261010
```

`--maintenance-confirmed` 是操作者对已完成维护的确认，脚本不自动停服务。
需要 MySQL `mysqldump`（可用 `--mysqldump=/路径/mysqldump` 指定）及足够的磁盘和备份权限。使用 MySQL 的 `--set-gtid-purged=OFF`；MariaDB 客户端需先验证兼容性，不得跳过备份。

备份目录 `/data/reopen-backups/<run-id>/` 包含：
- `database.sql`：完整数据库备份。
- `backup-manifest.json`：大小、SHA-256 和数据库目标。
- `plan.json`：初始返还明细和旧小号关联；后续步骤会核对文件摘要，不能修改或移动。
- `refund-completed.json` / `clean-completed.json` / `reset-subusers-completed.json` / `reset-servers-completed.json`：各步完成标记。

初次备份目录不能已存在，防止覆盖。若备份失败且 `status` 确认尚未建立批次，保留失败目录并另选备份根目录、沿用同一批次号重试备份。之后某一步失败，先查 `status` 再重试该步；不能重新备份或换批次来重复退款。退款已完成但清理未完成时，必须保持维护，防止玩家先使用返还余额。

## 必须留意

- **备份不因订单状态或扣款疑点被阻止。退款步骤中，旧数据没有 ptb_change、异常负向扣款等情况仍需核实。** 普通未支付订单不拦截退款，在清理步骤删除；有非零平台币变动的异常订单不能当作未支付单直接删除。先核实这些记录，不能把0变动盲目按 amount 再退。历史上单独做过补偿但原扣款仍保留的，需要人工对账，脚本无法推断两条流水是否已经冲抵。
- **其他现金直购**不会转换成平台币退款，这次只返平台币实际消费；现金礼包/Steam直购玩家是否另补偿需另定口径。
- **游戏服存档**不在本库。需要游戏服团队同步重置；否则旧角色可能重新上报。
- **Redis、登录票据、游戏会话、订单缓存、发奖去重缓存**需要按本服前缀核对清理/失效，不能对共享 Redis 直接 FLUSHALL。保留的一次性/长效票据可能指向旧角色或旧订单。
- **旧现金订单回调、补单重试、奖励定时任务**可能在恢复后再发货；必须设置赛季/重开边界或隔离旧任务。清掉礼包记录还会重置依赖该表的购买次数限制。
- **保留历史现金订单，日报/LTV清零后仍可能被 cron 重算出旧服金额**。如果新服统计需从零开始，需要单独设置统计起点/赛季，不能删除现金凭证来解决。
- **保留的现金/赠送/CDK记录可能含已删除的小号/角色ID**。这些旧关联不会强行改指向保留的小号；通过备份 plan 映射追溯。若数据库有外键从保留表引用待删对象，脚本阻止执行，需先制定归档方案。
- 目标表有触发器、非 InnoDB 表、循环外键等情况会阻止执行。大型日志表 DELETE 事务会占 undo/binlog 空间；先评估容量、维护窗口和复制延迟。
- 若需要永久限制每账号仅一个小号，或清封禁/设备绑定/管理员登录日志，需要另改业务配置，脚本不擅自处理。
- 本目录原本被 `.gitignore` 忽略；本次仅放行这三个重开脚本/测试/说明文件，其余部署产物继续忽略。

## 核对与恢复

先在隔离测试库试跑并试恢复备份。成功后核对返还总额、每账号余额及流水、每账号一个小号、角色为空；由运维确认缓存/游戏服/统计边界处理好后再恢复流量。
某一步失败发生在本步事务提交前会回滚该步，已成功的前序步骤不会自动撤销。提交后如需恢复，保持维护，把 `database.sql` 先恢复到隔离库核对，再按运维计划恢复原库；备份包含 `CREATE DATABASE/USE`，恢复时留意原库名。禁止直接在仍有新数据写入的生产库导入备份，否则会覆盖重开后的记录。重新恢复整个旧库时应一并处理备份后创建的 `server_reopen_runs/server_reopen_refunds`，不要留下与旧数据不一致的批次标记。
